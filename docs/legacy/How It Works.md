# How It Works

A step-by-step guide to understanding the Photobooth Guys Agreement Management System.

---

## What This Project Is

This is a web application for **Photobooth Guys** that helps manage client agreements (contracts) for photobooth events. Think of it as a central hub where:

- **Admins** create agreements, manage clients, and track who has signed what
- **Clients** receive links to view and sign their agreements online
- **Attendants** (event staff) see their upcoming jobs and get links to share with clients for backdrop selection

Everything is built with Next.js (a React framework), uses a PostgreSQL database, and connects to services like Stripe (payments), Google Drive (file storage), and optionally Bookly (WordPress booking plugin).

---

## The Three Main User Types

### 1. Admin (You)

You log in with a magic link sent to your email. Once in, you can:

- Create and edit agreement templates
- Add clients and their event details
- Create agreements from templates and send them to clients
- Track who has signed, who hasn?t, and when agreements expire
- Manage backdrop links (URLs clients use to pick backdrops)
- Organize attendants into groups and give them hub links
- Import events from a CSV (e.g., from Bookly)
- Generate quotes and manage leads
- View analytics and dashboards

### 2. Client (Your Customer)

Clients interact in two ways:

**A. Signing an agreement (no login)**

- You send them an email with a link like `yoursite.com/agreement/abc123`
- They open the link, read the agreement, and sign it
- After signing, they see a thank-you page where they can download a PDF or have it emailed

**B. Client portal (login required)**

- Clients go to `yoursite.com/portal` and enter their email
- They receive a verification code and log in
- They see a dashboard of their agreements, can update info, add notes, pay invoices (Stripe), pick backdrops, and more

### 3. Attendant (Event Staff)

Attendants use a special hub page:

- Link format: `yoursite.com/attendants/[group-slug]/hub` or `yoursite.com/attendants/[attendant-id]/hub`
- They see their upcoming jobs (agreements/events) for the day or week
- Each job links to an attendant page: `yoursite.com/attendant/[agreement-id]`
- On that page, they see client info and a backdrop link to share with the client

## Step-by-Step: How Things Flow

### Flow 1: Admin Logs In

1. You go to `/admin/login`
2. You enter your email (must match `ADMIN_EMAIL` in env)
3. NextAuth sends a magic link to that email
4. You click the link and are logged in
5. A JWT (token) is stored in your browser
6. Middleware checks this token on every `/admin/*` request (except login)
7. If no valid token, you?re redirected back to login

**Tech note:** Auth uses an in-memory adapter, not the database. Sessions are JWT-based. The `@next-auth/prisma-adapter` package is installed but not used.

---

### Flow 2: Creating and Sending an Agreement

1. **Create a client** (if needed)  
   - Admin ? Clients ? Add client with name, email, phone, event details

2. **Create an agreement**  
   - Admin ? Agreements ? Create new  
   - Pick a client and template  
   - Fill in any custom fields  
   - Agreement starts as **DRAFT**

3. **Send the agreement**  
   - Click ?Send?  
   - App calls `POST /api/agreements/send`  
   - Server merges template HTML with client/event data (smart fields like `{{client.firstName}}`)  
   - Status changes to **LIVE**  
   - Email is sent via Nodemailer (SMTP) with a link: `/agreement/[uniqueToken]`  
   - If email fails, you get a fallback link to copy and share manually

4. **Client receives the email**  
   - Clicks the link  
   - Lands on `/agreement/[token]`  
   - Page fetches agreement via `GET /api/agreements/client?token=...`  
   - View is tracked via `POST /api/agreements/track-view`

5. **Client signs**  
   - Clicks ?Sign?  
   - Enters name and email, agrees to terms  
   - `POST /api/agreements/sign` creates a Signature record and updates status to **SIGNED**  
   - Client is redirected to thank-you page

6. **Thank-you page**  
   - Client can download PDF or email it  
   - PDF is generated by `POST /api/agreements/pdf` (uses jsPDF)  
   - The page tries `pdf-pdfkit` and `pdf-js` first, but those routes **don?t exist**; only `/api/agreements/pdf` works

---

### Flow 3: Client Portal Login

1. Client goes to `/portal/login`
2. Enters email ? `POST /api/agreements/portal/request-access`
3. Server generates a 6-digit code, stores it temporarily, and emails it
4. Client enters code ? `POST /api/agreements/portal/verify-access`
5. Server creates a `ClientSession` with a session token
6. Token is stored in `localStorage` as `portal_session_token`
7. Client is redirected to `/portal/dashboard`
8. All portal API routes check this token via `getPortalSession()` in `portal/shared/auth.ts`

**Alternative:** Magic link login  
- Client can receive a magic link (e.g., from ?Gallery Ready? email)  
- Link includes `?token=...`  
- `POST /api/agreements/portal/magic-login` validates token and logs them in

---

### Flow 4: Client Portal Dashboard

1. Client is on `/portal/dashboard`
2. Page calls `GET /api/agreements/portal/dashboard`
3. Server returns all agreements for that client (by email)
4. Client sees grid/list of agreements with status, payment, gallery links, next actions, etc.
5. From there they can:
   - Open an agreement: `/portal/agreement/[id]`
   - Update profile: `POST /api/agreements/portal/update-client-info`
   - Add notes: `POST /api/agreements/portal/add-note`
   - Export data: `POST /api/agreements/portal/export`
   - Change preferences (e.g., layout): `POST /api/agreements/portal/preferences`

---

### Flow 5: Attendant Hub and Job Page

1. **Attendant hub** (`/attendants/[id-or-slug]/hub`)
   - `[id]` can be an attendant ID or an AttendantGroup slug
   - Page fetches jobs via `GET /api/attendants/[id]/jobs`
   - API finds agreements linked to backdrop links that contain this attendant?s ID, or agreements in events linked to this group
   - Shows upcoming jobs with client names, event dates, etc.

2. **Single job page** (`/attendant/[agreement-id]`)
   - Shows one agreement?s details
   - Displays backdrop link for the client
   - Link back to hub: `/attendants/[fromGroup]/hub`

**Note:** `/attendant/[id]` is the single job page; `/attendants/[id]/hub` is the hub. The redundant singular hub route was removed.

---

### Flow 6: Backdrop Links

- Backdrop links are URLs you configure (e.g., Typeform, Google Form) for clients to pick backdrops
- Stored in `BackdropLink` table
- Each link can be tied to an attendant ID
- Admin manages them at `/admin/backdrop-links`
- Agreements can have a `backdropLinkId` and `selectedBackdropName`
- When you pick a backdrop link for an agreement, the system can extract the attendant ID from the URL for the attendant hub

---

### Flow 7: File Uploads (Google Drive)

1. Admin uploads a file on the Clients page (max 4MB per file)
2. `POST /api/files/upload` receives the file
3. Uses `lib/google-drive.ts` to:
   - Find or create a folder for the client in Google Drive
   - Upload the file
   - Store metadata in `ClientFile` (clientId, eventId, googleDriveFileId, etc.)
4. Files can be attached to a client or to a specific event

**Setup:** You need OAuth2 credentials and a refresh token. The callback URL is `/api/auth/google/callback` (returns the auth code; you exchange it manually for tokens?see Google OAuth2 docs).

---

### Flow 8: Stripe Payments

1. Admin creates a Stripe invoice from an agreement: `POST /api/agreements/create-stripe-invoice`
2. Agreement gets `stripePaymentLink` and `stripeReceiptLink`
3. Client pays via Stripe
4. Stripe sends webhooks to `POST /api/webhooks/stripe`
5. Webhook handler updates agreement `paymentStatus` when payment succeeds

---

### Flow 9: Bookly Integration (Optional)

- **Bookly** is a WordPress booking plugin
- A PHP plugin in `app/api/agreements/bookly-agreements-integration/` can be installed on WordPress
- When a booking is created, it sends a webhook to `POST /api/agreements/bookly-webhook`
- The API creates or finds the client, creates an event, and optionally creates an agreement
- You can also import events manually via CSV at `/admin/events/import` (uses `papaparse`)

---

### Flow 10: Leads and Quotes

- **Leads** come from quote requests or manual entry
- Stored in `Lead` with stages: QUOTE_REQUESTED ? QUOTE_SENT ? AGREEMENT_SENT ? SIGNED ? COMPLETED (or LOST)
- Quote webhooks: `quote-inquiry` and `quote-sent` can create/update leads
- Admin manages leads at `/admin/leads`
- Quotes are generated at `/admin/quotes`; PDFs use jsPDF via `POST /api/quotes/generate-pdf`

---

## How the Database Fits In

- **Client** ? Core record (name, email, phone, etc.). Has deprecated event fields; prefer the **Event** model.
- **Event** ? Belongs to a client. Holds event date, type, location, package, price, etc.
- **Template** ? Agreement HTML and field definitions.
- **Agreement** ? Links client, template, and optionally event. Has status, token, Stripe info, gallery links, backdrop selection, etc.
- **Signature** ? Created when a client signs.
- **ClientSession** ? Portal login sessions.
- **ClientNote** ? Notes on clients or agreements.
- **BackdropLink** ? Backdrop selection URLs.
- **AttendantGroup** ? Groups of attendant IDs with a slug for hub URLs.
- **Lead** ? Pipeline/quote leads.
- **ClientFile** ? File metadata (actual files in Google Drive).
- **AuditLog** ? Activity log for agreements.
- **Settings** ? Key-value config.

### PDF Fallback Chain

The thank-you page (`/agreement/[token]/thank-you`) and admin preview (`/admin/preview/[token]`) use a 3-step PDF fallback:

1. `POST /api/agreements/pdf-pdfkit` ? **does not exist** (always fails)
2. `POST /api/agreements/pdf-js` ? **does not exist** (always fails)
3. `POST /api/agreements/pdf` ? **exists and works** (jsPDF)

So the first two calls always fail before the working one is used.

# Security Audit

## Credentials & API Keys

**No hardcoded passwords or API keys found.** All secrets are loaded from environment variables (`process.env`). The `.env.example` uses placeholders only.

## Potential Concerns

1. **Portal request-access when SMTP not configured:** The API returns `debugCode` (the 6-digit verification code) in the JSON response and logs it. This is intentional for development/setup when email can't be sent. In production with SMTP configured, the code is only emailed. **Recommendation:** Ensure SMTP is always configured in production.

2. **Console.log statements:** Many routes log tokens, agreement IDs, and request bodies. These don't expose passwords but could leak session/agreement tokens in server logs. **Recommendation:** Consider removing or gating debug logs behind `NODE_ENV` for production.

3. **track-view route:** Logs SMTP config (host, port, user?not password). Verbose but not a credential leak.

## NEXT_PUBLIC_ Variables

`NEXT_PUBLIC_BASE_URL` and similar are exposed to the client by design. The domain (photoboothguys.ca) is public information.
